# v1.2.5 design: connected devices

Status: agreed 2026-11-10 (decisions at the end). Work starts with step 1.

## What 1.2.5 is for

BE-Aero becomes one workspace across your machines (and later your phone). In your words:

1. **Networking:** BE-Aero instances on different machines find and trust each other.
2. **A VPN client** for secure connections.
3. **Syncthing-level file and state sync.**
4. **A file browser widget** that navigates this machine *and* your other devices.
5. **A File Pool** on every device: one folder that's shared across them all.
6. **An AI communications bus:** assistants on different devices send each other tasks,
   requests and queries.
7. **A phone companion**, as one more paired device. Design only in 1.2.5.

Also in 1.2.5, separate from the above: Windows app notifications in the notification
center, a Debian verification pass, and fixes from use.

Each of these needs the same foundation: **every device has an identity, devices pair
once, and paired devices talk over one secure channel.** Build that once and everything
else rides on it.

## 1. Device identity and pairing

- **Identity.** On first run each device makes a key pair and a self-signed certificate.
  Its **device ID** is the SHA-256 of that certificate, shown in groups
  (`MFZWI3D-BONSGYC-…`), the same scheme as Syncthing. Nothing central issues IDs, and
  an ID can't be faked without the private key.
- **Pairing.** This works like the existing local app API, where you approve each program
  once, but between devices:
  - Device A shows a short pairing code (and a QR code for the phone). Device B enters it.
  - Both sides show the other's name and ID, and you approve on both.
  - Each side then stores the other's certificate fingerprint. From then on, the channel
    accepts only that exact certificate.
- **Per-device permissions.** Each paired device gets its own permissions, as programs
  do today:
  - `files` (browse and transfer)
  - `pool` (the File Pool)
  - `state` (synced settings and notes)
  - `ai-bus` (send tasks and queries)
  - `notify` (push notifications)
  - `clipboard` (send to this device's clipboard)

  You can inspect, narrow or revoke each one in Settings > Devices.

## 2. The channel ("mesh")

- **Transport:** WebSocket over TLS 1.3 with **both sides pinned** (mutual TLS: each end
  checks the other's certificate fingerprint). Node has all of this built in, so nothing
  new ships. One connection per pair of devices, multiplexed. Messages are JSON with a
  type, plus binary frames for file chunks.
- **Finding each other on a LAN:** a small UDP announcement every 30 s (device ID and
  port, no secrets), the way Syncthing does local discovery. Addresses can also be typed
  in by hand.
- **Off the LAN:** devices reach each other over whatever already connects them: the
  VPN in section 3, Tailscale (you already run it), or Syncthing's relays (section 4).
  BE-Aero doesn't run a public server of its own.
- **Requests:** `files.list`, `files.stat`, `files.read` (chunked), `files.write`,
  `pool.status`, `bus.deliver`, `state.get`, `notify.push`, `clip.push`, `ping`. Each one is checked
  against the sender's permissions before it runs.

## 3. VPN: needs a decision

**minivpn (examples/minivpn-main) shouldn't ship.** Its own README says: "This
implementation is intended for research purposes only. It has serious flaws, so please
do **not** use it for any real-life situation where you need to trust it with user
data." It also lacks `tls-auth` and `tls-crypt`, which most real OpenVPN servers
require, and it's GPL-3.0.

What "a built-in VPN client" should be depends on what it's for:

| Purpose | Recommendation |
|---|---|
| **A. Let my BE-Aero devices reach each other securely from anywhere** | You get this without a system VPN. The mesh channel (section 2) is already end-to-end encrypted and pinned. Getting across the internet needs a route: Tailscale, Syncthing's relays, or a port you forward. No drivers, no admin rights. |
| **B. Connect this PC to my own VPN server** (home or office, OpenVPN or WireGuard) | A "VPN" widget that drives the **official** clients: WireGuard (`wireguard.exe /installtunnelservice`, `wg-quick` on Linux) or OpenVPN (`openvpn`, or `openvpn3` on Linux). You import a profile; the widget shows status, connect/disconnect and traffic. A real system VPN needs a network driver and admin rights, which the official clients already have and maintain. |
| **C. A built-in WireGuard mesh between my devices** (our own Tailscale) | Possible with `wireguard-go` (MIT) plus the Wintun driver on Windows. But it's a large security-sensitive component with an admin install; I'd do A first and only add this if A isn't enough. |

**My recommendation:** A now (it falls out of the mesh), B as the "VPN" widget in 1.2.5,
and C only if you still want it after using A.

## 4. File and state sync: Syncthing

**Use Syncthing itself rather than re-implementing it.** It's MPL-2.0, so it's fine to
ship alongside the app. It's mature and does the hard parts: conflict handling,
partial-file transfer, discovery, NAT traversal and relays. examples/syncthing-main is
the reference.

- **How it runs:** like Whisper and Piper. BE-Aero downloads the official release for
  the platform from Settings, checked against a pinned SHA-256, and runs it as a child
  process:
  - with its own home folder under BE-Aero's data folder
  - with its web interface off, and its REST API on 127.0.0.1 behind a generated API key
  - BE-Aero stops it on exit.
- **Pairing once does both.** When two BE-Aero devices pair, BE-Aero adds each one's
  Syncthing device ID to the other through the REST API and shares the Pool folder.
  You never see Syncthing's own pairing.
- **File Pool:** one folder per device, by default `~/BE-Aero Pool`, shared with every
  paired device that has `pool` permission. It shows up:
  - as a place in the file browser
  - as a drop target on the dock
  - in the AI's tools ("put the report in the pool")
- **State sync:** a second, hidden Syncthing folder holds selected state:
  - scratchpad notes
  - chat conversations
  - scheduled tasks (each pinned to the device that runs it)
  - pinned apps
  - theme

  - web widget states (the sites and their layout)

  **To avoid sync conflicts entirely, each device writes only its own file**
  (`state/<device-id>.json`), and every device merges all of them on read. Each entry is
  last-writer-wins, using the entry's own timestamp. Syncthing then never sees two
  devices editing one file.
- **Status:** shown per folder in the file browser and Settings > Devices (up to date,
  syncing x%, conflicts, device offline). The AI can read it as well.

## 4a. Send to device: clipboard

- **Send what's on your clipboard to a device.** Text, images or files go to another
  device's clipboard, with a notification there. Use the dock's device menu, the file
  browser's "Send to", a hotkey, or ask the assistant ("send this to my laptop").
- Needs that device's `clipboard` permission. Small items go straight over the mesh
  (`clip.push`); files over a size limit go through the File Pool, with the receiving
  clipboard holding the file.
- **Never automatic.** Nothing is mirrored without a "send", so passwords copied on one
  machine don't appear on the others.

## 5. File browser widget

A new desktop widget, in the same style as the other widgets:

- **Places sidebar:**
  - This PC: home, Desktop, Documents, Downloads, drives or mounts
  - File Pool
  - each paired device, with its own places (needs its `files` permission)
- **Main pane:**
  - list or grid view, breadcrumbs, search within a folder
  - sort by name, date or size
  - previews for images and text
- **Actions:**
  - open with the default app, reveal in Explorer or Files
  - copy or move between this PC, the Pool and other devices (transfers run over the
    mesh, with progress and resume)
  - new folder, rename, delete (to the Recycle Bin or Trash)
- **Permissions:** remote devices only expose the folders they've shared, never the whole
  disk unless you choose to. That's a per-device list in Settings > Devices.
- **AI:** tools `files_list`, `files_search` and `files_copy` across devices. These are
  read-only, except that copying asks first under the normal permission setting.

## 6. AI communications bus

A message channel between assistants on your devices, and later local programs (BE-Code)
and MCP clients.

- **Message:**
  ```json
  {
    "id": "...",
    "from": "<device>/<agent>",
    "to": "<device>/<agent>|*",
    "kind": "task|request|query|reply|event",
    "subject": "...",
    "body": "...",
    "replyTo": "<id>",
    "expires": "<time>",
    "attachments": ["pool:/path"]
  }
  ```
- **Storage:** one JSON file per message in an inbox folder, written atomically. This is
  BE-Code's `internal/inbox` design, and it means messages survive a restart or an
  offline peer. Delivery is over the mesh (`bus.deliver`), with retries until the message
  expires.
- **What the receiving assistant does depends on the kind:**
  - **Query:** answers read-only and replies.
  - **Request:** runs under that device's task permissions. The default is read-only; an
    "allow" needs your OK on that device.
  - **Task:** schedules work there (it appears in its task list, marked with the sender).
  - **Event:** recorded only.
- **Assistant tools:**
  - `bus_send`
  - `bus_ask`: send and wait for the reply, with a timeout
  - `bus_inbox`
  - `bus_reply`
  - `list_devices`

  For example: "ask the laptop's assistant whether its backup finished", or "have the
  Debian box re-run the weather task".
- **MCP surface (later in the release, or 1.3):** an MCP server exposing the bus and the
  file tools, so BE-Code or any MCP client can join as an agent.

## 7. Phone companion: design only in 1.2.5

The phone is **one more paired device on the same mesh**, not a separate API. The likely
shape is a small PWA served by BE-Aero, or a thin native shell. It would cover:
- pair by QR code
- notifications
- the File Pool
- chatting with any device's assistant over the bus
- quick actions

It needs one of the network routes in section 2 or 3 to reach your devices away from home.

## Also in 1.2.5

- **Windows app notifications:** read-only and best-effort. BE-Aero reads Windows'
  notification database
  (`%LOCALAPPDATA%\Microsoft\Windows\Notifications\wpndatabase.db`, SQLite) to mirror
  other apps' toasts into the notification center. It's undocumented, so it's
  behind a setting and fails quietly if its format changes. The supported route is a signed
  MSIX package with the `userNotificationListener` capability, which needs a code-signing
  certificate.
- **Debian verification pass:** media controls (MPRIS), Piper, Whisper, the GNOME dock
  helper and telemetry, tested over SSH and fixed as needed.
- **Fixes from use:** your list.

## Security summary

- Nothing new listens beyond the mesh port. It accepts only TLS connections from pinned,
  paired devices. Pairing needs a code shown on the other screen, plus your approval on
  both sides.
- Every request is checked against that device's permissions. Revoking a device drops its
  connection and removes it from Syncthing.
- Remote file access is limited to folders you've shared. Incoming AI requests and tasks
  follow the receiving device's permission settings, never the sender's.
- Downloaded components (Syncthing) are pinned by SHA-256, the same as Whisper.

## Decisions (2026-11-10)

1. **VPN: A.** Devices connect over the encrypted, pinned mesh, crossing the internet
   via Tailscale, Syncthing relays or a forwarded port. There's no OS-level VPN, and
   minivpn isn't used. B and C are left for later, if wanted.
2. **Syncthing: managed binary**, downloaded and pinned by SHA-256, with its web
   interface off, and driven by BE-Aero.
3. **State sync by default:**
   - scratchpad notes
   - theme and pinned apps
   - AI conversations
   - scheduled tasks (each runs on its own device)
   - web widget states

   Plus **send-to-device clipboard** (section 4a).
4. **Remote file access: only the File Pool** until you share more folders per device.
